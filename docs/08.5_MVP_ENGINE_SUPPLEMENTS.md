# Vassnian — 08.5 MVP Engine Supplements

## Purpose
Systems to **scaffold into the engine during MVP** even though MVP content won't use them. Building these now prevents refactoring later. Each section shows what to build now vs what the demo fills in.

> **MVP Philosophy:** Make everything WORK. No variety, no images, no balancing. Just a system that's easy to add to. All UI correct. Architecture matches vision.

---

## 1. Derived Combat Stats (Data-Driven)

Primary stats (STR, VIT, etc.) must feed into **derived stats** like Spell Power, Physical Power, etc. These derived stats are what skill damage formulas reference.

**Build now:**
```rust
pub struct DerivedStatFormula {
    pub stat_id: String,           // "spell_power"
    pub display_name: String,      // "Spell Power"
    pub base_value: f32,
    pub scaling: Vec<StatScaling>,
}

pub struct StatScaling {
    pub from_stat: String,    // "intelligence"
    pub multiplier: f32,      // 1.5
}
```

**JSON** (`data/config/stat_formulas.json`):
```json
{
  "derived_stats": [
    {
      "stat_id": "spell_power",
      "display_name": "Spell Power",
      "base_value": 0,
      "scaling": [{ "from_stat": "intelligence", "multiplier": 1.5 }]
    },
    {
      "stat_id": "physical_power",
      "display_name": "Physical Power",
      "base_value": 0,
      "scaling": [
        { "from_stat": "strength", "multiplier": 1.5 },
        { "from_stat": "dexterity", "multiplier": 0.5 }
      ]
    },
    {
      "stat_id": "healing_power",
      "display_name": "Healing Power",
      "base_value": 0,
      "scaling": [{ "from_stat": "faith", "multiplier": 2.0 }]
    }
  ]
}
```

Skills reference derived stats in damage formula:
```json
{ "type": "damage", "base": 40, "scaling_stat": "spell_power", "multiplier": 1.0 }
```

**MVP:** Define system + JSON. Knight only uses `physical_power`. Everything else scaffolded.

## 2. Base Skill Architecture (Extensible)

Skills must have a **common base** so adding new skills is trivial. Support:
- Combat skills (active, passive, toggle)
- World skills
- **Class-exclusive** skills (only that class can learn)
- **Universal** skills (learnable via skill books if stats met)
- Future: skill trees for caster vs non-caster classes

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum SkillExclusivity {
    ClassOnly,        // only this class can ever use it
    LearnableByAll,   // anyone can learn via skill book if stats met
}
```

Add `exclusivity` field to `CombatSkillDef`. Default: `LearnableByAll`.

**MVP:** Build the field. All MVP skills are `LearnableByAll` (none exist yet anyway).

## 4. Item Level & Category System

Items need **levels** and **rarity** for random shop generation and loot tables.

```rust
pub enum ItemCategory {
    Weapon { weapon_type: String, damage_formula: String },
    Armor { defense: i32, slot: EquipSlot },
    Accessory { stat_bonuses: StatBlock },
    Potion { effect: PotionEffect, target: TargetType },
    KeyItem { description: String },                    // keys, quest items — description only
    CraftingMaterial { used_at: String },                // "blacksmith", "mage"
    SkillBook { skill_id: String },
}

pub enum ItemRarity {
    Common,     // random drops, shop stock
    Uncommon,   // better drops
    Rare,       // mini-boss drops, special quests
    Unique,     // one-of-a-kind, story items
}
```

**Item data rules:**
- Key = has description only (no stats)
- Weapon = has damage formula
- Potion = has heal/damage amount
- Level = used for random shop generation later

**MVP:** Build structs. MVP items: 1 weapon (Common, level 1), 2 potions (Common, level 1).

## 7. Story Script System

Some stories need **special scripting** beyond choice→branch:

| Script Type | Example |
|-------------|---------|
| Random selection | 3 random NPCs appear, pick 1 |
| Forced battle outcome | You lose but survive (scripted loss) |
| Party split | Player separated from group (solo segment) |
| Timeline jump | Memory monster — story starts mid-way with jumps |

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type")]
pub enum StoryScript {
    RandomSelect { pool: Vec<String>, count: usize },
    ForcedBattleOutcome { outcome: String },   // "lose_but_survive"
    TemporaryPartySplit { who_leaves: Vec<String> },
    TimelineJump { node_order: Vec<String> },
}
```

Add optional `scripts: Vec<StoryScript>` field to `StoryNode`. Default: empty.

**MVP:** Define enum. No MVP stories use scripts.

## 10. Mission Selection System

Before each mission, player chooses from **3 options** with different difficulties:
- Each option has a short description
- Difficulty indicated by time cost
- If it's a companion story, companion's name/portrait appears next to it
- Skipping a companion story = you lose it permanently

```rust
pub struct MissionOption {
    pub story_id: String,
    pub description: String,
    pub difficulty: MissionDifficulty,
    pub time_cost: i32,
    pub is_companion_story: Option<String>,  // companion_id if yes
    pub has_special_item: bool,
}

pub enum MissionDifficulty { Easy, Medium, Hard }
```

**MVP:** Build struct. MVP has no mission selection (linear stories). System ready for demo.

## 11. Story Setup System (New Game Initialization)

At new game start, a story list is pre-generated:
- **Fixed events:** All bosses, mandatory events (King intro, companion choices)
- **Random pool:** Everything else randomized
- **Continuation priority:** When a multi-part story is completed, its sequels immediately take random slots and kick out other stories
- **Failure handling:** If a mission fails and has no continuation path, the sequels disappear and random stories replace them

```rust
pub struct StoryPool {
    pub fixed_stories: Vec<String>,       // always present
    pub random_pool: Vec<String>,         // available for random selection
    pub active_continuations: Vec<String>, // sequels from completed stories
    pub available_missions: Vec<MissionOption>, // current 3 choices
}
```

**MVP:** Build struct. MVP has fixed linear story order. System ready for demo randomization.

## 12. City / Shop Access Rules

| Location | Shop Button | Rules |
|----------|------------|-------|
| Overworld (outside Shadow World) | **Always visible** | Can always go to city, costs time |
| Shadow World — normal mission | **Hidden** | Can't shop during mission |
| Shadow World — underground city | **Visible** | Part of mission, trade allowed |
| Shadow World — meet merchant | **Visible** | Part of mission, trade allowed |

```rust
pub struct MissionContext {
    pub allows_shop: bool,       // does this story node allow shop access?
    pub allows_city: bool,       // can player return to main city?
    pub current_terrain: Terrain,
}
```

**MVP:** Shop is entered via story choice (existing system). Add `allows_shop` flag to story nodes.
